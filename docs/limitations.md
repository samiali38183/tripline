# Scope and limitations

What the current numbers mean, and what they do not.

## Scope of a "pass"

A scenario passes when **every expected rule fires on at least one event** of its fixtures. That
is a recall check on a known-good recording. It says nothing about:

* **Precision.** No benign corpus is replayed yet, so a rule that fires on everything also passes.
  Phase B adds benign corpora and a false-positive budget per rule.
* **Robustness.** Each scenario is one procedure. `chmod u+xs` already showed how literal the
  vendored rules are (`docs/findings.md` F-001); the mutator (Phase B) will generate evasion
  variants and score how many still fire.
* **Timeliness, alert routing, or response.** tripline stops at the rule verdict.

## Coverage numbers

* The prevalence weights (1-10) come from the Red Canary 2026 Threat Detection Report's technique
  ranking, mapped by hand in `scenarios/*.yaml`. They are a reasonable proxy for "what actually
  happens", not a measurement of this environment.
* "Weighted coverage of all scenarios" treats *pending* scenarios as 0 - it is a progress metric
  for this repository, not a claim about an organisation's coverage.
* 14 scenarios cover 14 techniques. ATT&CK Enterprise has over 600 (sub-)techniques; the heatmap
  colours only what tripline has evidence for and leaves everything else blank on purpose.

## Telemetry

* **Cloud** fixtures are replayed from public detonation datasets (Stratus Red Team, flaws.cloud),
  re-timestamped and tagged. They are real CloudTrail records but were not generated by this
  project's own account, and some data-plane events (S3 `GetObject`) are absent from the public
  datasets, so T1530 is detected via the exposure and enumeration events rather than bulk reads.
* **Linux** fixtures are recorded on `ubuntu-latest` with auditd `execve` + cron watches only.
  There is no file-integrity, network or syslog telemetry, and the runner is a single-user VM, so
  rules that depend on user context or lateral activity cannot be exercised there.
* **Windows** fixtures (when present) are recorded on `windows-latest` with Sysmon
  (SwiftOnSecurity config), Security 4688/4698 and PowerShell 4103/4104. Defender is relaxed for
  the run, so a tactic that Defender would block on a hardened host still produces telemetry here.
  Endpoint-protection evasion is out of scope.
* Runner noise is real: 20-40 wrapper processes per atomic. Scores are reported as "N of M
  applicable events" and never require that a rule fire *only* on the malicious event.

## Evaluator

* The Python compiler supports the Sigma constructs listed in the README and raises on anything
  else; `keywords` lists and aggregation expressions are rejected rather than approximated.
* A rule whose logsource no fixture event satisfies reports `0/0 applicable events` and does not
  fire. The gate fails because the expected rule missed, but the message is a routing failure, not
  a detection failure - read the applicable count.
* Field names are mapped per collector shape (`tripline/logsource.py`). A production pipeline
  with different field names needs its own router entry; there is no generic ECS/OCSF mapping.
* Case-insensitive string matching follows Sigma semantics; regular expressions are
  case-sensitive unless the rule says otherwise. There is no backend-specific escaping, so a rule
  that works here may need adjustment for a specific SIEM query language.

## Reproducibility

* `tripline replay --all` is deterministic from a checkout: no network, no clock.
* `tripline cloud build` is reproducible from the public datasets as long as the upstream URLs
  resolve; the flaws.cloud tarball is ~450 MB and is cached under `.cache/`.
* Emulation workflows are *not* bit-reproducible: Atomic Red Team, Sysmon and the runner image
  move. That is intended - the weekly runs exist to catch drift - and the committed fixtures pin
  the snapshot the scorecard was computed from (source run URL in each `manifest.json`).

## Known gaps (grey on the heatmap)

* T1114.003 (mail forwarding rule), T1564.008 (mail hiding rule): need a mail tenant.
* T1204.004 (ClickFix-style user execution): needs a human at the keyboard; the Windows
  scenarios cover the *resulting* PowerShell execution, not the social-engineering step.
